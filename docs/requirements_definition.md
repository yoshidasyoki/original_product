# 要件定義
オリプロで作成するアプリの要件定義（機能要件・非機能要件）を行う。

## 1. 要件定義
### 作成アプリのターゲット
- 自部署3Dプリンターを使用するすべての利用者
（自部署内＋他部署社員。現時点では10人/月程度）

### 解決したい課題
#### ① 自部署の人が自由に3Dプリンターを使用できず、業務上支障をきたすことがある
自部署で管理を行っている機械であり、最初は空いている時間帯のみ貸し出す形で運用を始めた。しかし他部署の利用が想定以上に増えてしまい3Dプリンターの利用がひっ迫してしまった。
現段階ではoutlookでの先着予約性となっているので、どんどん他部署の人に予約を入れられてしまい自部署内で不満が高まっている。

#### ② メンテナンス管理を忘れてしまい機械が定期的に故障する  
使用している3Dプリンターは一定の稼働時間を過ぎると部品交換が必要であったり、月次点検もする必要がある。そのため稼働時間や前回点検日などを細やかに記録する必要があるのだが、業務が忙しくてほとんど記録されずに放置・壊れたら初めて取り換えるという状態が慢性化してしまっている。  
→ 事後保全になってしまい業務が停滞している＝解決の手立てが必要。

### 課題要因の深堀り
#### ① 自部署の人が自由に3Dプリンターを使用できず、業務上支障をきたすことがある
- 利用者に優先順位がなく、予約の早い者勝ちになっている
- 予約の占有や仮押さえが一部見受けられる（先約主義が原因か？）
- 利用の需要と供給のバランスがあっていない  
（3Dプリンター1台で工場内のすべての従業員が使用できる状態→台数増やすべきでは？）

#### ② メンテナンス管理を忘れてしまい機械が定期的に故障する
- 利用予約から都度稼働時間を算出してスプレッドシートに記載...→面倒！
- 業務が忙しく、メンテナンスのことを考える余裕がない

### 得られた要因に対する解決法
それぞれの要因から考えられる対策法を挙げていく。

#### ① 自部署の人が自由に3Dプリンターを使用できず、業務上支障をきたすことがある
- 予約を承認制とする（自部署内メンバーを承認者とすれば優先して使用できる）
- 予約の利用制限を設けて一部ユーザの占有を防ぐ
- 3Dプリンターの台数を増やしてもらう ← 予算的に厳しいとの回答

#### ② メンテナンス管理を忘れてしまい機械が定期的に故障する
- 予約時の情報から稼働時間を自動算出して交換の目安時期を知らせる
- 月次点検に関しても点検時期のお知らせ機能をつける

### 課題の解決方法
挙がった解決案をもとに、今回のアプリ開発では以下のような形での実装を目指す。
- 予約を承認制とする（自部署内メンバーを承認者として優先使用できるようにする）
- 予約の利用制限を設けて一部ユーザによる占有を防ぐ
- メンテナンス管理はアプリが自動で行う。管理者はアプリを開くだけでいつメンテナンスすべきかを分かるようにする

## 2. 機能要件の洗い出し
課題解決に向けて必要な機能の洗い出しを行う。
まず、今回はゲストユーザ、一般ユーザ、管理者ユーザの3タイプを用意する形とする。  
以下の表のような形で、ユーザごとに操作できる権限を切り分ける運用を想定。

|                  | ゲストユーザ | 一般ユーザ | 管理者ユーザ |
| ---------------- | ----------- | --------- | ----------- |
| 予約状況の閲覧    | 〇          | 〇         | 〇          |
| 利用予約          | ✕          | 〇         | 〇          |
| 予約承認          | ✕          | ✕         | 〇          |
| メンテナンス関連*¹ | ✕          | ✕         | 〇          |
| ユーザ登録        | ✕          | △*²       | 〇          |
| ユーザ権限編集     | ✕          | ✕         | 〇          |

*¹ 累計稼働時間の確認、メンテナンス記録の閲覧・追加・編集・削除、メンテナンスの通知などメンテナンスに必要となる情報の閲覧・操作が行える権限
*² ユーザ登録を行った後、管理者ユーザの承認を経て初めて一般ユーザの権限を付与することができる

なお、各ユーザはそれぞれ以下のような使用を想定。
- ゲストユーザ＆一般ユーザ：他部署利用者に対して割り振るアカウント権限
- 管理者ユーザ：自部署に対して割り振るアカウント権限

さらにもう少し、アプリに必要な機能をピックアップしていく。

### ゲストモード
ログインしていない状態では予約一覧のみ確認できるようにする
（トップページのみ表示させるイメージ）

### 一般ユーザ機能
他部署の利用者を想定して機能をリストアップ
- ユーザ登録 / ログイン
- アカウント情報の編集
- 予約の追加 / 編集 / キャンセル
- パスワード再発行

### 管理者機能
自部署の利用者を想定して機能をリストアップ
- 一般ユーザの機能はすべて利用可
- 管理者アカウント追加（既存管理者による承認制）
- 予約の権限設定（自動予約 or 承認制、切り替えできるようにする）
- 予約が入ったときの通知機能（承認制のときのみ）
- 仮パスワード発行（問合わせの対応）
- 機械の使用時間管理とメンテナンス通知

### 予約機能
予約時の大まかな流れを書き出して整理

- 土日祝は分かるように色分け
- 1時間単位で予約可能
- キャンセル操作は予約者本人が実施
- 重複予約は不可

### 承認フロー
自動承認と承認制の２パターンの動作をリストアップ

#### 自動承認
- 予約に空きがあれば常に承認扱い
（承認ステータスは「承認済」とする）
- 管理者（自部署利用者）による予約は承認フローに寄らず承認される

#### 承認制
- 予約が入ると承認ステータスが「承認待」となり承認許可を待つ
- 管理者が予約を承認or拒否する

### メンテナンス管理
3Dプリンターのメンテナンス時に欲しい機能をリストアップ
- 定期点検の実施日を記録する
- 定期点検の記録は簡潔に行えるようにする
- ノズル交換時からの稼働時間を予約履歴から自動算出する
- 一定の稼働時間を超えた場合は通知する

## 3. 非機能要件
非機能要件のリストアップも行っていく。

### UX・UI
- 現状ではPCで業務を行うパターンがほとんどなのでPC限定でレイアウト作成を行う
（PCサイズの範囲でレイアウトが崩れないようレスポンシブデザインにする）

### 可用性・拡張性
- 障害時やメンテナンス時を考慮してWEBサーバは2台で運用する
- オートスケール機能は実装しない
※ 1日のアクセス数は現状10人程度、増えても30~40人ほどでアクセス負荷は小さいと見込まれるため
- マルチAZなしで運用を行う
※ 基幹システムではないので一定の障害リスクは許容できる

### 運用・保守
- 異常処理はログに記録する
- `CloudWatch`でインフラリソースの監視を行う
※ 異常監視を行う ＋ 運用経験がないので選択したインフラリソースが適切かを確認するために導入
- 静的解析ツールを導入してコード品質を担保する
- CI/CDを導入して変更に対応しやすいシステム構成とする

### セキュリティ
- 通信はHTTPSのみ許可する
- 権限に応じてアクセスできるページに制限をかける
- パスワードはハッシュ化して保存する
- DBには機密情報を含むので外部からの直接アクセスは禁止する
- パスワード再発行処理は紛失者が管理者に問い合わせ → 管理者が発行した仮パスワードを用いて設定する形とする
※ パスワードリセットメールの導入も考えたが導入コストが高いと判断

### データベース管理
- 重要な処理はトランザクション処理で整合性を保つ
- 排他制御を用いて予約の重複を防ぐ
- 必要箇所に参照制約（外部キー制約）を設定して整合性を確保する
